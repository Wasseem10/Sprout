3. REQUIRED USER EXPERIENCE

Initial launch: Sprout is awake and ready, with microphone off until explicitly activated. Microphone off does not universally mean asleep: text interaction must still work normally.

Idle: quiet breathing, occasional blink and restrained gaze. No random celebration or unnecessary bouncing.

Listening: attentive forward engagement and lifted buds. Quiet open listening remains eligible for the inactivity timeout. An open conversation by itself must not keep Sprout awake forever.

Thinking: the existing contemplative asymmetric pose during real processing, transcription or task work. Do not invent financial meanings for gestures.

Speaking: an expressive but planted explaining gesture, detailed below. It must correspond to actual spoken output, not merely a TTS request waiting on the network.

Success: one existing JoyJump after a genuinely completed task, scheduled at the reply boundary described below. Then return to the latest real state. Do not stack Done nod and JoyJump for the same result.

Sleep: existing recline with feet forward, happy closed eyes and floating/fading Zs. Capture and playback must already be stopped. Do not make the old blue eyelid surfaces return.

Wake: existing recovery and eye opening, smoothly returning to current activity. Starting the microphone must never wait for this animation to finish.

4. AUTOMATIC INACTIVITY AND MANUAL PAUSE

Implement a 120,000 ms eligible-inactivity deadline. Eligibility includes mic-off idle and silent open listening. Reset activity on meaningful interaction with the companion: typing/editing, activation clicks or taps, relevant keyboard commands, transcript scrolling, accepted user speech, and starting a task or conversation.

Do not reset the deadline from hover/pointer tilt, animation frames, blinking, renderer callbacks, polling, rerenders, status announcements, or arbitrary RMS/noise samples. Outside desktop activity that the app cannot observe is not an input to this policy.

Use accepted non-echo realtime transcript events and the existing sustained VAD detection in the batch fallback as voice activity. Preserve current barge-in/echo rules. Do not accidentally change the existing partial-transcript interruption threshold while exposing activity. The installed useScribe API does not have the separate useConversation product's onVadScore/getInputVolume callbacks; inspect installed types and do not invent SDK APIs.

Block inactivity sleep during microphone connection/permission setup, a genuine utterance in progress, transcription, active/in-flight work, pending or playing reply audio, Wake, and a completion celebration. Start a fresh two-minute eligible window once those operations settle. An utterance-in-progress signal must clear correctly on commit, failure, cancellation and session change so it cannot hold the app awake indefinitely.

At timeout, recheck the latest activity revision, busy state and generations. Pause through the existing voice owner FIRST, then request SleepEnter -> SleepLoop. This must stop tracks, disconnect Scribe, cancel pending voice requests and stop output just as the existing Pause operation does. Do not merely change the icon, meter, gain or canvas pose.

Manual microphone Pause has immediate effect on capture and playback:
- If no task is running, enter sleep immediately after media cleanup is initiated.
- If a task is already running, let it continue and retain Thinking. Record a pending rest intention; do not call the backend Stop endpoint or abort the task merely because the user paused voice.
- When that task settles, a fresh successful completion may do its one short joy cue, then sleep. Failure goes directly to rest with its accessible error information preserved.
- New typing, a new task or explicit microphone activation clears pending rest. Output-mute toggles and decorative hover do not.
- Explicit Pause during an already queued/playing celebration or after completion cancels that decorative cue and enters sleep when no work remains.

Keep these controls independent:
- Pause microphone/conversation: stop input and output; request rest under the policy above.
- Mute spoken replies: stop/disable output only; input stays active, and this alone does not request sleep.
- Pause avatar motion / reduced motion: change presentation only; never acquire/release mic resources or cancel a task.
- Stop task: preserve existing cancellation behavior; do not reinterpret it as proof of success.

5. WAKING AND MEDIA RACES

Clicking the mic or using its keyboard/global shortcut explicitly wakes Sprout and calls the existing startConversation path. Do not call resumeConversation after Pause: it currently returns when conversation is off. Do not introduce a competing session manager.

Capture may connect while Wake runs. A mere phase change to starting/listening must not instantly cancel Wake as the current setPhase behavior can do. Genuine incoming speech, transcription or new work may smoothly preempt it. Audio capture and interruption responsiveness have priority over presentation.

Typing/submitting while asleep wakes Sprout for text use WITHOUT opening the microphone. Hover, focus, opening the panel, restoring visibility, canvas recovery or a renderer callback must never silently start capture. Merely opening the panel may leave Sprout sleeping until a meaningful interaction occurs.

Permission failure leaves an awake, truthful mic-off/error presentation. Preserve accessible error feedback; do not silently retry. Preserve drafts, selection and reading position across sleep/wake and panel transitions.

Handle Pause -> Resume -> Pause, delayed token/permission responses, late microphone streams, stale transcripts, late TTS responses, fallback switching and stale playback-ended callbacks. Reuse existing voice/task generations and cleanup. Old work must not restart a stopped session, submit a stale command, trigger a stale jump or wake Sprout.

6. COMPLETION JOY WITHOUT COMPETING ANIMATIONS

Retain BuddyCompletionGate's confirmed task.status === 'completed', task-ID deduplication, hydration seeding and request-generation guards. HTTP success, finishing a spoken sentence, a generic chat reply, receiving an import result or clearing busy are not proof of task completion.

Audit all existing accepted-result paths that can return a fresh completed task, including the primary request and relevant existing bill/import operations. Apply a consistent observer only where the existing contract provides confirmed completion. Do not redesign those operations or celebrate unrelated state synchronization.

For each accepted success, keep at most ONE pending completion cue, tied to its task/request identity and, where applicable, that task's final reply lifecycle:
- Associate that reply lifecycle atomically with acceptance of the successful result, before clearing busy or evaluating a no-reply celebration. Avoid a success -> no pending audio -> premature jump gap before speak() starts.
- If the result has no spoken reply, celebrate after work settles.
- If there is pending/playing final reply audio, let the distinct speaking animation finish first, then celebrate once. Never delay, truncate or cancel the answer to show the jump.
- Reply mute/skip or TTS failure may settle the reply boundary; backend success remains success. Explicit microphone Pause, Stop, new user speech/new work or dismissal supersedes the pending decorative cue as specified above.
- A spoken acknowledgment at task start is not the final reply boundary. An unrelated/stale audio-ended event cannot release the cue.
- Awaiting voice.speak(...) is not that boundary: its current Promise resolves after playback starts. Observe the matching final reply's actual ended/error/skip/cancel lifecycle, with explicit no-reply handling.
- Keep the pending cue through a legitimate long associated reply; do not reuse the current Done cue's one-second expiry unchanged. Discard it when its identity is superseded, its presentation surface is dismissed/hidden, or its generation becomes stale. No general animation queue and no replay on returning later.
- Mark it consumed exactly once. Quiet active listening is allowed during JoyJump; manualEligible must not reject/cancel this automatic success simply because the voice session is open.
- Actual new speech/work smoothly preempts JoyJump from its current visible pose. Return to the latest real state, not the state captured when the jump began.

If reduced motion, motion pause or no WebGL prevents celebration, consume the cue and retain the accessible completion message. Do not queue it for a later surprise jump. Pending rest must still proceed when joy is skipped/dropped, including while hidden; never wait indefinitely for a renderer callback that cannot arrive. Keep Sprout_Done in the asset for compatibility/Studio if needed; it must not duplicate the automatic celebration.
